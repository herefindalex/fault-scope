**Інтерактивна лабораторія для вивчення коректності розподілених застосунків.**

FaultScope спирається на докази й контракти системи, щоб з’ясувати, що можна гарантувати після збою. Кожен кейс спочатку визначає властивість, яку треба зберегти, а потім межу, де потрібне виправлення.

## Вісім кейсів

1. [Чи слід надіслати повторно?](docs/cases/fs-c01.md) — Відповідь не надійшла, але VM, можливо, вже створено. Подальші дії визначає контракт.
2. [Чи може A записати результат після передачі задачі B?](docs/cases/fs-c02.md) — Worker B перебрав Job J, але A досі працює. Чи матиме результат A силу, вирішує перевірка в Job Store під час запису.
3. [Замовлення підтверджено. Де Event E?](docs/cases/fs-c03.md) — У PostgreSQL Order42 вже має стан CONFIRMED, але процес аварійно завершується до публікації Event E. Який стійкий запис дозволить опублікувати E пізніше?
4. [Споживач завершив обробку. Чому він запустився знову?](docs/cases/fs-c04.md) — Запланована винагорода та відсутність підтвердження можуть призвести до того, що одна логічна подія відбудеться двічі.
5. [Яка подія насправді новіша?](docs/cases/fs-c05.md) — Пізніша доставка може мати старіший стан. Знайдіть орган, який наказує змінити одне відправлення.
6. [Читання успішне. Дані достатньо актуальні?](docs/cases/fs-c06.md) — Успішна відповідь може бути занадто старою для цього абонента. Перенесіть прийняту редакцію до прочитаного контракту.
7. [Скасування справді зупинило роботу?](docs/cases/fs-c07.md) — Сигнал скасування надійшов, але результат передачі може залишатися заблокованим. Знайдіть операцію, яка має брати участь.
8. [Система перезапустилася. Що вона забула?](docs/cases/fs-c08.md) — Shipment42 все ще каже SHIPPED після збою. Ревізійний охоронець, який його захищав, зник.

Кожен кейс має режими «З підказками», «Виклик» і «Поглиблений розбір», окрему візуалізацію, панель «Докази / Контракт / Властивість» і сім ракурсів коду. Прогрес кожного кейсу зберігається в браузері.

## Запуск FaultScope

Опубліковану версію можна запустити через `./faultscope`. Щоб зібрати поточну попередню версію з коду, виконайте:

```bash
go run ./tools build
./dist/faultscope
```

Відкрийте [http://localhost:8080/](http://localhost:8080/). За замовчуванням `:8080` прослуховує всі мережеві інтерфейси. Іншу адресу задайте через `./dist/faultscope --listen 127.0.0.1:9000` або `FAULTSCOPE_LISTEN=127.0.0.1:9000`; параметр командного рядка має пріоритет. Для збирання потрібні Node 24 і pnpm 12. Дивіться [посібник розробника](docs/development/getting-started.md).

## Стан і архітектура

Це **попередня версія `0.0.x`**, у якій опубліковано кейси 01–08. Приклади з VM, завданнями, замовленнями, повідомленнями та винагородами є навчальними моделями, а не робочими SDK чи інфраструктурою. Для всіх 20 мов наявні повні повідомлення інтерфейсу й восьми кейсів; 19 перекладів іншими мовами, окрім англійської, залишаються **бета-версіями без перевірки технічними фахівцями — носіями мови**. Мову інтерфейсу й ракурс коду обирають незалежно. Сім ракурсів: **Go, TypeScript, Python, Java, PHP, C і C++**. Інтерфейс Next.js/React збирається в статичні файли та вбудовується в один виконуваний файл Go. Під час роботи не потрібні сервер Node, база даних, каталог вмісту чи служба перекладу. Налаштування та прогрес зберігаються лише в браузері.
