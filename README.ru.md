**Интерактивная лаборатория для изучения корректности распределённых приложений.**

FaultScope помогает по имеющимся свидетельствам и контрактам системы понять, что можно гарантировать после сбоя. В каждом кейсе сначала формулируется свойство, которое нужно сохранить, а затем находится граница, где требуется исправление.

## Восемь кейсов

1. [Следует ли отправить повторно?](docs/cases/fs-c01.md) — Ответ не пришёл, но VM, возможно, уже создана. Следующий шаг зависит от контракта.
2. [Может ли A записать результат после передачи задачи B?](docs/cases/fs-c02.md) — Worker B перехватил Job J, но A продолжает работать. Решение о том, действителен ли результат A, принимает Job Store при записи.
3. [Заказ подтверждён. Где Event E?](docs/cases/fs-c03.md) — В PostgreSQL Order42 уже имеет статус CONFIRMED, но процесс падает до публикации Event E. Какая постоянная запись позволит опубликовать E позже?
4. [Потребитель завершил обработку. Почему он запустился снова?](docs/cases/fs-c04.md) — Зафиксированное вознаграждение и отсутствие подтверждения могут привести к тому, что одно логическое событие произойдет дважды.
5. [Какое событие действительно новее?](docs/cases/fs-c05.md) — Более поздняя доставка может содержать более старое состояние. Найдите орган, который заказывает изменения в одной отправке.
6. [Чтение прошло успешно. Данные достаточно актуальны?](docs/cases/fs-c06.md) — Успешный ответ может быть слишком старым для этого вызывающего абонента. Внесите зафиксированную редакцию в контракт чтения.
7. [Отмена действительно остановила работу?](docs/cases/fs-c07.md) — Поступил сигнал отмены, однако передача результата может остаться заблокированной. Найдите операцию, которая должна участвовать.
8. [Система перезапустилась. Что она забыла?](docs/cases/fs-c08.md) — Shipment42 по-прежнему отображает SHIPPED после сбоя. Охранник ревизии, защищавший его, исчез.

В каждом кейсе есть режимы «С подсказками», «Задача» и «Подробный разбор», отдельная визуализация, панель «Свидетельства / Контракт / Свойство» и семь представлений кода. Прогресс по каждому кейсу хранится в браузере.

## Запуск FaultScope

Готовую версию можно запустить командой `./faultscope`. Чтобы собрать текущую предварительную версию из исходников, выполните:

```bash
go run ./tools build
./dist/faultscope
```

Откройте [http://localhost:8080/](http://localhost:8080/). По умолчанию `:8080` прослушивает все сетевые интерфейсы. Другой адрес можно задать через `./dist/faultscope --listen 127.0.0.1:9000` или `FAULTSCOPE_LISTEN=127.0.0.1:9000`; параметр командной строки имеет приоритет. Для сборки нужны Node 24 и pnpm 12. Подробнее в [руководстве для разработчиков](docs/development/getting-started.md).

## Состояние и архитектура

Это **предварительная версия `0.0.x`** с опубликованными кейсами 01–08. Примеры с VM, заданиями, заказами, сообщениями и наградами — учебные модели, а не производственные SDK или инфраструктура. Для всех 20 языков доступны полные сообщения интерфейса и восьми кейсов; 19 переводов, кроме английского, остаются **бета-версиями без проверки профильными носителями языка**. Язык интерфейса и представление кода выбираются независимо. Доступны семь представлений: **Go, TypeScript, Python, Java, PHP, C и C++**. Интерфейс Next.js/React собирается в статические файлы и встраивается в один исполняемый файл Go. Во время работы не нужны сервер Node, база данных, каталог содержимого или сервис переводов. Настройки и прогресс остаются только в браузере.
